Dev aur test same distribution se

Dev set ka kaam hai model choices karwana. Test set ka kaam hai final honest report. Dono future user data jaise hone chahiye, aur ideally same distribution se sample hone chahiye.

Dev/test size aaj ke zamane mein

Purane chhote data era mein 60/20/20 split common tha. Big data mein test/dev ko huge rakhna zaroori nahi. Bas itna ki metric reliable ho.

Total labelled examplesReasonable split ideaNote
1,000700 train, 150 dev, 150 testHar example precious
1,00,00098,000 train, 1,000 dev, 1,000 testDev/test enough stable
1 crore99.8 lakh train, 10k dev, 10k testTiny percentage bhi kaafi

Rule percentage ka nahi, confidence ka hai. Agar dev set mein only 50 examples hain, 1 galti se metric 2% hil jayega. Agar 10,000 examples hain, 1 galti sirf 0.01%.

Metric kab badalna?

Kabhi model metric ke hisaab se jeet raha hota hai, par product sense ke hisaab se loser hota hai. Tab metric badlo.

Maan lo customer-support triage model tickets ko queue mein bhejta hai. Model A ka overall error kam hai, par prepaid order refund tickets galat queue mein bhejta hai. Model B ka overall error thoda zyada, par refund misses kam. Agar refund miss 6 guna mehenga hai, metric ko weighted banao.

weighted error = normal routing mistakes + 6 ? refund-miss mistakes
  • normal routing mistakes = aam ticket galat queue mein gaya
  • refund-miss = refund ticket urgent queue mein nahi gaya
  • 6 = product/team ka cost weight; domain ke hisaab se choose hota hai
ModelNormal mistakesRefund missOld error countWeighted error
A9099990 + 6×9 = 144
B1123115112 + 6×3 = 130

Old metric A ko winner bolta tha. Weighted metric B ko. Agar business reality B ke favour mein hai, metric update karna sahi hai.

Pehle nishaana tay, phir nishaana lagana

Do alag kaam hain:

Nishaana tay karnaDev/test distribution aur metric choose karna. “Humein kya optimize karna hai?”
Nishaana laganaModel train/tune karna. “Is target pe best score kaise laayein?”

Beginner galti: metric galat nikla to bhi model tune karte rehna. Senior move: ruk ke target fix karo, phir tuning pe jao.

Dev set user data jaisa na ho to?

Agar dev set old product ka data hai aur ab app naye users ke liye launch ho rahi hai, dev set badlo. Haan, pehle wale experiments se comparison toot sakta hai. Par galat compass pakad ke chalne se better hai compass reset karna.

Simple rule: Dev set woh duniya dikhaye jahan tum model ko improve karna chahte ho. Test set usi duniya ka final honest sample ho.
Dhyan rakhna: Test set pe baar-baar model choose mat karo. Test set ko board exam jaise treat karo — final mein kholna, daily mock test nahi.
Yaad rakhna: Dev/test setup model se pehle ka decision hai. Galat target pe best model bhi product mein flop lag sakta hai.

Dimaag mein aaye sawaal

Sirf dev set rakhein, test nahi?

Early research ya internal prototype mein kabhi okay hai. Par public number report karna hai, paper/product launch hai, ya stakeholder promise hai, to separate test set rakho.

Dev aur test size equal hone chahiye?

Nahi. Dono reliable hone chahiye. Agar final report pe high confidence chahiye to test bada rakho. Hyperparameter tuning zyada hai to dev bhi stable rakho.

Metric badalne se cheating lagti hai?

Agar test pe result dekh ke metric apne favour mein badla, cheating. Agar product pain samajh aaya aur team openly metric update kare, woh good engineering hai.

✍️ Ab tumhari baari (pehle khud socho, phir answer kholna)

10,000 example dev set mein 230 mistakes. Error kitna? Ek extra mistake se kitna change?

Error = 230/10,000 = 2.3%. Ek extra mistake = 1/10,000 = 0.01%. Final answer: 2.3%, change 0.01%.

Model A: 60 normal mistakes, 7 refund misses. Model B: 82 normal, 2 refund misses. Refund weight 5. Winner?

A weighted = 60 + 5×7 = 95. B weighted = 82 + 5×2 = 92. Final answer: B.

Food-photo app ke dev set mein restaurant menu photos hain, users ghar ki plate photos bhejte hain. Kya karo?

Dev/test ko user-style ghar ki photos se refresh karo. Menu photos training mein useful ho sakti hain, par target dev/test nahi. Final answer: dev set badlo.
