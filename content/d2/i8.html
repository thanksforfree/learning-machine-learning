Dataset 50 lakh examples ka hai. Har gradient step se pehle sab data dekhna padega?

Agar har chai sip se pehle poori ketli naapoge, chai thandi ho jayegi. Mini-batch ka idea: thoda data dekho, ek useful step lo.

To gradient exact nahi hoga?

Exact nahi, par kaafi useful. Thoda shor hoga, par speed bahut badhegi.

Batch vs mini-batch notation

Batch gradient descent har step mein saare m examples use karta hai. Mini-batch gradient descent data ko chhote packets mein todta hai: X{1}, Y{1}; X{2}, Y{2}; ... Har packet pe forward/backward/update hota hai.

X{t} = t-th mini-batch of X Y{t} = matching labels mini-batch size = examples per packet
  • t = mini-batch number
  • X{t} ka shape often (nₓ, mini_batch_size)
  • Last batch chhota ho sakta hai

Epoch ka matlab

Ek epoch = model ne training set ke har example ko roughly ek baar dekh liya. Agar 1000 examples aur batch size 128, to ek epoch mein 8 updates honge. 10 epochs ka matlab same dataset ke 10 chakkar, har chakkar shuffle ke baad nayi grouping ho sakti hai.

Cost graph shor wala kyu hota hai

Batch gradient descent mein har point full dataset cost pe based hota hai, graph smooth lag sakta hai. Mini-batch mein ek batch easy ho sakta hai, next batch tough. Isliye cost kabhi down, kabhi thoda up. Trend downward hona chahiye, har mini-step perfect nahi.

Batch size choices

Batch size = mPure batch. Gradient stable, par huge data pe slow per update.
Batch size = 1Stochastic. Fast updates, bahut noisy, vectorization ka fayda kam.
Beech wala64, 128, 256, 512 jaise sizes. Speed aur noise ka practical balance.

Mini-batch size ko powers of 2 rakhna common hai, kyunki hardware/memory pe friendly hota hai. Par rule stone pe likha nahi. Sabse bada sawaal: GPU/CPU memory mein fit ho raha? Training stable hai?

Size kaise chunein: 64 se 512

Small datasets mein full batch bhi okay. Large datasets mein 64, 128, 256, 512 se start karo. Agar batch memory mein fit nahi, size ghatao. Agar GPU underused hai aur memory bach rahi, size badha ke throughput improve ho sakta hai.

def random_mini_batches(X, Y, size=128):
    m = X.shape[1]
    perm = np.random.permutation(m)       # pehle shuffle
    Xs, Ys = X[:, perm], Y[:, perm]
    batches = []
    for k in range(0, m, size):
        batches.append((Xs[:, k:k+size], Ys[:, k:k+size]))
    return batches                         # last batch chhota ho sakta

Shuffle + partition

Shuffle zaroori hai. Agar data sorted hai — pehle 500 cricket photos, phir 500 football photos — aur tum batches bina shuffle banate ho, first batches sirf cricket dikhayenge. Gradients biased ho jayenge. Shuffle se har mini-batch dataset ka chhota mixed sample banne ki koshish karta hai.

Dhyan rakhna: X aur Y ko same permutation se shuffle karo. X alag shuffle, Y alag shuffle hua to labels galat examples se chipak jayenge. Ye silent disaster hai.
Yaad rakhna: Mini-batch training poore data ka intezaar nahi karti; chhote samples se noisy par useful kadam leti hai.

Dimaag mein aaye sawaal

Mini-batch gradient descent hamesha full batch se better?

Large data pe usually practical better. Chhote data pe full batch simple aur stable ho sakta hai. Hardware aur dataset size decide karte hain.

Cost mini-batch pe plot karun ya epoch average?

Dono useful. Mini-batch plot noisy signal deta hai; epoch average cleaner trend dikhata hai.

Last mini-batch chhota ho to drop karna hai?

Usually use kar sakte ho. Batch norm jaisi cases mein very tiny last batch issue de sakta hai, tab drop_last option useful ho sakta hai.
