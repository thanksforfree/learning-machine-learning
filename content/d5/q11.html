Beam search samajh aa gaya. Par long sentence ki probability naturally chhoti hoti hai. Phir model short answer ko unfair advantage dega?

Bilkul pakda. Har extra word ek number 1 se chhota multiply karta hai. Isliye practical beam search logs aur length normalization use karta hai.

Aur output achha hai ya nahi, woh kaise judge karun?

Human judgement best hai, par automatic metric bhi chahiye. Translation mein famous metric hai BLEU. Thoda jugaadu, par useful.

Products chhote hote hain, logs friendly hote hain

Probability multiply karte karte 0.0000002 jaise numbers aa jaate hain. Computer underflow kar sakta hai, aur compare karna awkward hota hai. Log trick: product ka log = logs ka sum.

log score(y) = Σ⟨t⟩ log P(y⟨t⟩ | y⟨1⟩, ..., y⟨t−1⟩, x)
  • Product maximize karna aur log product maximize karna same ordering deta hai.
  • Log probabilities negative hoti hain, par add karna stable hota hai.
CandidateProbabilitylog(probability)
I feel hungry0.172−1.760
I am hungry0.065−2.733

Log score −1.760 better hai kyunki zero ke zyada paas hai.

Length normalization: short answer ko free medal mat do

“haan” ek word ka answer high probability le sakta hai, par translation incomplete ho sakti hai. Isliye score ko length se normalize karte hain. Common form mein α ≈ 0.7 use hota hai.

normalized score = (1 / Tyα) × Σ⟨t⟩ log P(y⟨t⟩ | ...)
  • Ty = output length
  • α = length penalty ka knob; 0 ho to no normalization
  • Score ab bhi log space mein hai; bada matlab better.
SentenceRaw probTyα = 0.7 normalized log
A: “I ate rice”0.0723log(0.072) / 30.7 = −1.219
B: “I ate rice today”0.05044log(0.0504) / 40.7 = −1.132

Raw probability A ki zyada thi, par length-normalized score B ko prefer kar raha hai. Matlab longer but complete sentence ko fair chance mila.

B kaise choose karein?

B = 1 fast hai, par greedy. B = 3 ya 10 toy/project mein common. B = 100 zyada careful search. B = 1000 bahut mehenga, aur improvement usually slow ho jaata hai. Real choice latency, memory, vocabulary size, aur quality trade-off pe depend karti hai.

Small BFast, mobile app jaisa setup, par good candidate miss ho sakta hai.
Large BBetter search coverage, par decoding slow. Model galat ho to large B bhi galat ko polish karega.
Dhyan rakhna: Beam search best output ki guarantee nahi deta. Ye approximate search hai. Top path early prune ho gaya to wapas nahi aata.

Error analysis: beam ki galti ya model ki?

Ek input x ke liye human/reference answer y* hai. Beam ne ŷ diya. Ab model se dono probabilities nikaalo.

CaseModel comparisonDosh kiska?
1P(y* | x) > P(ŷ | x), par beam ne ŷ chunaBeam search ne good path miss kiya
2P(y* | x) < P(ŷ | x)Model khud wrong output ko zyada pasand kar raha hai

Ye doctor wali diagnosis hai. Fever hai to pehle pata karo viral hai ya food poisoning. Har problem ka ilaaj same nahi hota.

BLEU: ek answer nahi, kai sahi translations

Translation mein ek hi correct answer nahi hota. “Main ghar ja raha hoon” ko “I am going home” ya “I’m heading home” dono bol sakte. BLEU candidate ko multiple reference translations se compare karta hai.

BLEU ka core idea: candidate ke n-grams references mein mil rahe hain kya? Par cheating rokne ke liye modified precision clipping use hoti hai. Agar candidate “very very very” bolta rahe, references mein “very” ek baar hai to count ek hi milega.

TextSentence
CandidateI feel hungry after school today
Reference 1I am hungry after class today now
Reference 2I am hungry after school right now
Reference 3I became very hungry after school today

Geometric mean = exp((log 0.833 + log 0.600 + log 0.500 + log 0.333)/4) = 0.537. Candidate length c = 6, closest reference length r = 7, to brevity penalty lagta hai.

BP = exp(1 − r/c) agar c ≤ r; warna BP = 1 BLEU = BP × exp((1/4) × Σ log pₙ)
  • BP = brevity penalty; bahut chhota candidate punish hota hai
  • pₙ = modified precision for n-grams, usually n = 1 se 4
  • Yahan BP = exp(1 − 7/6) = 0.846, BLEU = 0.846 × 0.537 = 0.455.
import math
p = [5/6, 3/5, 2/4, 1/3]
geo = math.exp(sum(math.log(x) for x in p) / 4)
bp = math.exp(1 - 7/6)   # candidate chhota hai
print(bp * geo)           # 0.455 ke aas-paas
Yaad rakhna: Logs stability dete hain, length normalization fairness deta hai, aur BLEU rough automatic score deta hai — human judgement ka replacement nahi.

Dimaag mein aaye sawaal

BLEU high hai to translation perfect?

Nahi. BLEU n-gram overlap dekhta hai, meaning nuance nahi samajhta. Par dataset-level comparison ke liye useful signal hai.

Length normalization mein α 0.7 hi kyu?

Ye common practical value hai. Tune kar sakte ho. α low hoga to short sentences ko advantage, high hoga to length ka effect zyada compensate hoga.

Error analysis mein y* ki probability kaise nikaalun?

Teacher forcing jaisa: reference y* ke words model ko step by step feed karo aur un words ki probabilities multiply, ya log-sum, kar lo.

✍️ Ab tumhari baari (pehle khud socho, phir answer kholna)

Candidate probability 0.02 aur length 5 hai. α = 0.7. Normalized log score approx kya? (50.7 ≈ 3.08)

log(0.02) ≈ −3.912. Divide by 3.08: −1.27 approx.

Agar P(y* | x) = 0.30 aur P(ŷ | x) = 0.45, galti beam ki ya model ki?

Model ki. Model wrong ŷ ko reference se zyada probability de raha hai.

Candidate “very very tasty” aur reference “very tasty” hai. Word “very” ka clipped count kitna?

Reference mein “very” max 1 baar hai, to clipped count 1, candidate mein 2 baar hone ke baad bhi.
